## v0.1 이후

### v0.2 — 중간지점 독립 도구 (2주)

**검증할 가설:** 검색 유입이 발생하는가

`/middle` 경로의 독립 도구. "강남역 홍대입구역 중간지점" 같은 쿼리로 유입시킨 뒤
결과 화면 하단의 "이 장소들로 코스 만들기" 버튼으로 본 제품에 유도합니다.
경쟁 기능을 마케팅 채널로 쓰는 구조입니다.

**핵심 제약 — 순진하게 만들면 서비스가 성립하지 않습니다.**
5명 × 후보역 10개 = 요청당 API 50건. 경로 API 무료 쿼터가 일 1,000건이므로
하루 20명이면 소진됩니다.

해법은 소요시간 그래프를 자체 보유하는 것입니다:

1. **사전 구축(1회)** — 공공데이터포털의 수도권 전철 역간 거리·소요시간 데이터로
   노드 약 800개 그래프 구성. 환승 페널티 4~5분. JSON으로 서버 메모리 상주(수백 KB)
2. **요청 시** — 각 출발지를 최근접 역에 매핑 → 다익스트라 전 역 대상 실행
   (API 호출 0건, 수십 ms) → 후보별 `max(개인 소요시간)`과 표준편차로 상위 3곳 선정
3. **검증** — 최종 3곳만 실제 대중교통 경로 API로 확인 (요청당 15건)

요청당 50건 → 15건. 무료 쿼터로 하루 60명 이상 처리 가능합니다.

> **좌표 산술평균은 절대 쓰지 않습니다.** 강북과 강남의 중간점은 한강 한복판으로
> 찍힙니다. 사용자가 원하는 것은 기하학적 중간이 아니라 **시간이 공평한 지점**입니다.
> 이 차이가 기존 중간지점 서비스 대비 유일한 차별점입니다.

루프가 그 자리에서 끊긴다는 판단은 그대로입니다. 서버와 도메인 규칙을 한 벌로 두고
웹·앱이 같이 씁니다.

안드로이드는 한참 뒤입니다. iOS를 먼저 공개합니다.

## 성공 지표

### 핵심

**생성된 지도 1개당 평균 조회수 — 목표 3.0 이상**

이 값이 1.0 근처면 공유가 일어나지 않는 것이고, 제품 가설이 틀린 것입니다.
v0.1 배포 직후부터 이 숫자만 봅니다.

```sql
select
  count(*) as maps,
  sum(view_count) as views,
  round(avg(view_count), 2) as views_per_map
from maps;
```

### 보조

| 지표 | 측정 방법 | 상태 |
|---|---|---|
| 지도 생성 완료율 | 생성 시작 대비 저장까지 도달 | 미구현 |
| 드로잉 사용 비율 | 획이 1개 이상인 지도 비율 | 쿼리로 즉시 가능 |

```sql
-- 드로잉 사용 비율
select round(100.0 * count(distinct s.map_id) / nullif(count(distinct m.id), 0), 1) as pct
from maps m left join strokes s on s.map_id = m.id;
```
